## Fixed interface and bounded behavior

Preserve the approved interface: `OwnerContext { userId: string; assurance: "aal2" }` and `requireOwner(request: Request): Promise<OwnerContext>`. Identity and assurance must derive from the same provider-verified session/token; current owner authorization comes from the authoritative database row. A request body, email string, editable metadata, cookie decode or valid token alone is not owner authority. Missing/invalid/expired identity is 401; verified but non-owner/AAL1/revoked is 403. Denials disclose no private owner/table data. Provider/database failure fails closed and is reported honestly rather than treated as successful authorization.

1. Build local Supabase configuration, CLI-generated migrations and generated database types. Disable public signup. The authoritative `admin_users` relation uses the verified auth UUID, constrained owner role and active state; users cannot insert themselves, change roles or reactivate access. Document separately controlled initial owner enrollment. Synthetic local test enrollment is permitted; production owner enrollment/project provisioning is not.
2. Implement request-scoped server/browser clients, verified identity, live owner lookup and AAL2 enforcement on every protected private read/mutation. Ordinary data calls retain the user's token and RLS. Keep any privileged fixture/setup client out of production data paths and browser imports. No role-authority cache survives requests or owner revocation.
3. Implement login, controlled first-factor MFA enrollment/challenge/verification, refresh and logout, then a minimal protected admin landing. Initial owner/factor bootstrap is separately controlled and test-only in this packet. For an owner with an established factor, AAL1 cannot enroll/verify a substitute factor, remove/reset the established factor or invoke recovery to bypass it; subsequent factor management requires current-owner AAL2. Probe the provider's direct SDK/Auth API as well as UI guards. If the pinned local provider cannot enforce this, return the exact reproduction and bounded security proposal; do not claim a UI-only guard closes it. The neutral `src/app/admin/layout.tsx` must not guard its own login/MFA routes. Guard only the `(protected)` layout and its server operations. Authentication setup flows provide no private admin data and cannot widen OwnerContext to AAL1. Validate return destinations; avoid redirect loops/open redirects. No editor, preview, publishing or rollback.
4. Implement guarded admin auth API endpoints within `src/app/api/admin/auth/**`. Each endpoint declares and enforces its own admission rule: login accepts unauthenticated requests; enrollment/challenge requires verified identity plus current owner authorization but permits AAL1; private admin operations require full OwnerContext/AAL2. Setup responses expose no private application records. A page layout or client redirect does not protect an API. Enforce request-origin/CSRF boundaries for login/MFA/logout and state-changing handlers against explicit configured origins, not an untrusted Host header. Document safe handling of missing origins and callback state/PKCE. Add durable bounded login throttling through approved local infrastructure; no process-local counter is claimed durable.
5. Use least-privilege grants and RLS for every actually exposed protected table, view and callable function. Record separate USING/WITH CHECK conditions and operation grants. Keep any owner-check helper narrowly scoped with a fixed search path, qualified relations, limited execution privileges and no caller-controlled authorization identity. Avoid recursive policies or permissive-policy OR bypasses. Normal owner access must not use service-role bypass.
6. Revoke the authoritative owner row while keeping an otherwise-valid AAL2 session. After the revocation transaction commits, the next fresh guarded request and database operation must deny without waiting for token expiry or refresh. Test revocation between the app guard and database write as well; RLS remains the final boundary. Do not claim cancellation of already-completed or pre-commit operations.
7. Keep auth/refresh/private responses out of shared caches, and isolate cookies/client instances across users. Do not log bearer/cookie/refresh/MFA secrets; redact QR screenshots and configuration output. Provider logout/token-lifetime semantics are documented, not replaced by unsupported claims of instant token invalidation. Public semantic pages remain useful if auth is unavailable.

Consult current primary documentation and installed command help before implementation: [SSR identity/cookie handling](https://supabase.com/docs/guides/auth/server-side/creating-a-client?queryGroups=framework&framework=nextjs), [MFA enforcement](https://supabase.com/docs/guides/auth/auth-mfa), [grants/RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [local database tests](https://supabase.com/docs/reference/cli/supabase-test-db). Record the exact supported SDK/CLI versions selected in the harness and dependency proposal. The accepted package has no Supabase dependency; do not silently replace its package/lockfile or add a global cookie-refresh proxy. Return exact integration diffs, including narrowly matched refresh wiring, for a single-owner integrator.

| --- | --- |

Preserve intentionally public sanitized reads such as future `published_content`; the private-table denial matrix must not silently remove the established public-read contract.

For **every actual protected table**, independently assert all four operations for all five identities:

| Identity | Protected read/mutation outcome |
| --- | --- |
| Anonymous | Denied |
| Authenticated non-owner, including one with MFA | Denied |
| Active owner without MFA / AAL1 | Denied |
| Active owner with valid AAL2 | Allowed only for the table's authorized operations |
| Revoked owner with otherwise-valid AAL2 session | Denied on the next operation after committed revocation |

An active owner does **not** gain role/enrollment/activation writes to `admin_users`. Test those writes as denied too. Positive controls prove allowed owner reads and any actually authorized mutations succeed on the same real relation/fixtures. If a table permits no normal owner DML, say so; do not manufacture broad CRUD grants to obtain a PASS.

Seed existing sentinel rows and verify affected counts plus privileged before/after state. RLS may deny reads/updates/deletes with zero rows rather than an exception; a 200 response or empty table is insufficient evidence. Test policy checks under the actual anon/authenticated roles, not only postgres/service-role. SQL claim simulation is policy evidence; real provider-issued signed tokens/MFA and direct Data API/app tests establish identity integration. Forge cookies, role/profile fields, old tokens and helper arguments; they must not grant access.
