Interaction language
We should establish strict rules so users learn intuitively.
Visitor action	Meaning
Move pointer	environment awareness
Hover	discoverability
Click/tap	interact
Drag	physical manipulation
Scroll	cinematic/navigation progression
Escape	return/back
Keyboard	accessibility + terminal
Hold	optional secondary interaction


Avoid double-click because mobile doesn't translate elegantly.

Interactions must compose
This is one of the biggest architectural requirements.
Suppose:
- blinds are closed
- lamp is off
- headphones are on
- CandidateX activates
The application should understand the combined state.
Not reset the room every time.
We therefore need separation between:
WORLD STATE
CHARACTER STATE
CAMERA STATE
PROJECT STATE
AUDIO STATE
UI STATE

Example:
world.lamp = false
world.blinds = closed

character.action = coding

camera.position = HOME

project.active = none

audio.enabled = true

ui.overlay = none

That's much stronger than one giant global currentScene.

We need an interactable registry
Every interactive 3D entity should register metadata.
Conceptually:
{
  id: "wall-painting",
  type: "environment",
  actions: ["hover", "click", "drag"],
  cameraResponse: "micro",
  priority: 20,
  cooldown: 0,
  accessibleLabel: "Interactive wall painting"
}

Character:
{
  id: "ayush-avatar",
  type: "character",
  actions: ["hover", "click"],
  cameraResponse: "medium",
  priority: 70,
  cooldown: 7000,
  accessibleLabel: "Ayush working at his desk"
}

CandidateX:
{
  id: "candidatex-monitor",
  type: "project",
  actions: ["hover", "click"],
  cameraResponse: "transition",
  priority: 90
}

This lets interaction scale to dozens of objects without chaos.

Accessibility equivalents
Crucial.
If painting moves when pointer touches it, that's fun.
But project access cannot depend on being able to interact with 3D geometry.
So every meaningful item also exists in normal DOM navigation.
Example:
3D microphone
        ↕
HTML "Yor Talks" link

Screen-reader users get complete content.
Keyboard users can focus room objects.
Reduced-motion visitors receive a shortened response.
Mobile interactions
Mobile needs a different interaction vocabulary.
No hover.
Therefore:
desktop:
hover → preview → click
mobile:
tap → preview/select
tap again/CTA → enter
or preferably:
tap object → short animation + contextual button.
Dragging objects still works with pointer events when appropriate.
Haptics
On supported devices, extremely subtle vibration could accompany selected interactions in a native wrapper, but for normal web this isn't something I'd make foundational.
The visuals need to work without it.

Then we can find out whether visitors actually explore.

The final goal
The user should eventually be able to spend five minutes in the room without opening a single project and still enjoy themselves.
But someone in a hurry should be able to reach CandidateX in two clicks.
That's the balance.
The site needs two simultaneous identities:
A playground for curious visitors.

and
A brutally efficient portfolio for recruiters.

That is the interaction standard I would add to the Astra brief. The critical new subsystem is an Interaction Bible covering every significant room object with idle → proximity/hover → click/tap → active behavior → camera response → character response → audio response → content outcome → cooldown → mobile behavior → accessible equivalent. Once we define that matrix for the full room, we will know exactly what has to be modeled, animated and engineered before production begins.
